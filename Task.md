# Задание 3. «Что изменилось на странице?»

Разработайте сервис периодического наблюдения за изменениями веб-страниц.

Пользователь выбирает одну или несколько страниц, задает интервал проверки и при необходимости указывает элементы страницы, изменения которых нужно игнорировать.

Сервис должен периодически загружать страницы, сохранять их версии и показывать, что именно изменилось относительно предыдущего состояния.

Основная схема:

```text
пользователь добавил URL
        ↓
scheduler
        ↓
очередь заданий
        ↓
worker pool
        ↓
HTTP GET
        ↓
HTML
        ↓
ignore list
        ↓
нормализация
        ↓
сравнение с предыдущей версией
        ↓
история + diff
```

## 1. Добавление страницы

Пользователь самостоятельно выбирает страницу для наблюдения.

Для каждой страницы необходимо задать минимум:

```text
URL
интервал проверки
ignore list
```

Например:

```text
URL:
https://example.com/news

Interval:
30s

Ignore:
.current-time
.advertisement
#view-counter
```

Допускается наблюдение за несколькими страницами одновременно.

---

## 2. Требования к странице

Страница должна быть доступна по HTTP/HTTPS без обязательной авторизации.

Отслеживаемое содержимое должно присутствовать непосредственно в HTML-ответе сервера.

Поддерживать страницы, содержимое которых появляется только после выполнения JavaScript, не требуется.

Работа строится по схеме:

```text
HTTP GET
→ HTML
→ разбор DOM
→ текст
→ сравнение
```

Использовать браузер, Selenium, Playwright и аналогичные инструменты не требуется.

---

## 3. Периодическая проверка

Каждая страница проверяется через заданный интервал.

Например:

```text
/news   — каждые 30 секунд
/prices — каждые 2 минуты
/status — каждые 10 секунд
```

Небольшое отклонение от точного момента запуска допустимо.

Медленная проверка одной страницы не должна блокировать остальные.

---

## 4. Очередь заданий

Scheduler не должен сам выполнять HTTP-запросы.

Его задача:

```text
определить, что страницу пора проверить
↓
создать job
↓
поставить job в очередь
```

Проверки выполняются ограниченным worker pool:

```text
                  scheduler
                      |
                      v
                bounded queue
                      |
            +---------+---------+
            |         |         |
            v         v         v
         worker    worker    worker
            |         |         |
            v         v         v
           HTTP      HTTP      HTTP
```

Очередь должна иметь ограниченный размер.

Например:

```text
queue size = 100
workers = 20
```

Количество workers задает максимальное количество одновременно выполняющихся HTTP-проверок.

---

## 5. Состояние проверки страницы

Для одной страницы одновременно не должно существовать несколько одинаковых проверок.

Недостаточно хранить только:

```text
running = true / false
```

Пока задача стоит в очереди, worker еще может ее не выполнять.

Поэтому необходимо минимум три состояния:

```text
idle
queued
running
```

Жизненный цикл:

```text
idle
  ↓ scheduler
queued
  ↓ worker забрал job
running
  ↓ проверка завершилась
idle
```

Если scheduler срабатывает, когда страница уже:

```text
queued
```

или:

```text
running
```

новая задача не создается.

Пример:

```text
interval = 10s
HTTP request = 27s

00s → queued
01s → running

10s → running → skip
20s → running → skip

28s → idle
30s → queued
```

Переход:

```text
idle → queued
```

должен выполняться конкурентно безопасно.

---

## 6. HTTP-запрос

Для загрузки используйте Go HTTP client.

Необходимо корректно обрабатывать:

```text
2xx
4xx
5xx
timeout
DNS error
connection error
TLS error
```

Ошибка одной страницы не должна останавливать сервис.

После ошибки страница должна проверяться снова через следующие интервалы.

---

## 7. Timeout

Каждый HTTP-запрос должен иметь ограничение времени.

Например:

```text
request timeout = 5s
```

Медленный сайт не должен навечно занимать worker.

Используйте:

```go
context.Context
```

---

## 8. Работа только с HTML

Сервис отслеживает HTML-страницы.

Не требуется отслеживать:

```text
PDF
изображения
видео
архивы
другие бинарные ресурсы
```

Тип содержимого необходимо определять по HTTP-ответу, а не только по расширению URL.

Например:

```text
/resource
Content-Type: application/pdf
```

не является HTML-страницей, несмотря на отсутствие `.pdf` в URL.

---

## 9. Ограничение размера HTML

Нельзя бесконтрольно читать страницу любого размера целиком в память.

Необходимо установить:

```text
max HTML size
```

Например:

```text
2 MB
```

Если HTML превышает лимит, проверка получает отдельный результат:

```text
html_too_large
```

Это не должно автоматически считаться:

```text
broken link
```

если сервер успешно ответил `200 OK`.

Необходимо различать:

```text
HTTP / network error
```

и:

```text
локальное ограничение crawler'а
```

---

## 10. Разбор HTML

Сравнивать сырой HTML целиком недостаточно.

Например:

```html
<h1>
    Новости
</h1>
```

и:

```html
<h1>Новости</h1>
```

визуально содержат одно и то же.

Перед сравнением необходимо:

1. разобрать HTML;
2. применить ignore list;
3. извлечь текст;
4. нормализовать пробелы и переносы строк;
5. получить стабильное представление страницы.

---

## 11. Ignore list

Пользователь самостоятельно определяет, какие элементы страницы не участвуют в сравнении.

Ignore list содержит CSS-селекторы.

Например:

```text
.current-time
.advertisement
#view-counter
.recommendations
```

Типичные исключения:

```text
таймер
текущее время
счетчик просмотров
рекламный баннер
случайная рекомендация
динамический блок
```

Сервис не должен самостоятельно угадывать, что является рекламой или счетчиком.

Это решение пользователя.

Алгоритм:

```text
HTML
↓
DOM
↓
найти элементы из ignore list
↓
удалить их
↓
извлечь текст
↓
нормализовать
↓
сравнить
```

---

## 12. Изменение ignore list

Пользователь должен иметь возможность изменить ignore list уже существующей страницы.

После изменения правил необходимо определить, относительно какой версии выполняется следующее сравнение.

Рекомендуемый вариант:

```text
ignore list изменился
↓
текущая страница обрабатывается заново
↓
создается новая baseline version
```

Чтобы изменение настроек само по себе не выглядело как изменение сайта.

Выбранное поведение необходимо описать в README.

---

## 13. Хранение версий

Для успешных проверок необходимо сохранять версии страницы.

Минимально:

```text
page_id
checked_at
HTTP status
normalized content
```

Дополнительно можно сохранять:

```text
original HTML
hash
content size
```

Количество хранимых версий следует ограничить.

Например:

```text
последние 20 версий
```

---

## 14. Определение изменений

После получения новой версии необходимо сравнить ее с предыдущей.

Было:

```text
Версия 1.5
Исправлено 12 ошибок
```

Стало:

```text
Версия 1.6
Исправлено 17 ошибок
Добавлена поддержка Linux
```

Результат:

```text
- Версия 1.5
- Исправлено 12 ошибок
+ Версия 1.6
+ Исправлено 17 ошибок
+ Добавлена поддержка Linux
```

Недостаточно вывести:

```text
страница изменилась
```

Пользователь должен увидеть конкретный diff.

Можно использовать готовую библиотеку diff.

---

## 15. Неизменившаяся страница

Если нормализованное содержимое совпадает:

```text
previous == current
```

создавать новую полную версию необязательно.

Но факт проверки должен сохраниться:

```text
12:00 initial
12:30 unchanged
13:00 unchanged
```

---

## 16. История проверок

Необходимо сохранять историю:

```text
12:00 initial
12:30 unchanged
13:00 changed
13:30 timeout
14:00 HTTP 500
14:30 changed
```

Для `changed` должен быть доступен diff.

Для ошибки:

```text
тип ошибки
время
HTTP status при наличии
```

---

## 17. Persistence

Данные должны переживать перезапуск приложения.

Допускается:

```text
SQLite
PostgreSQL
```

или другое постоянное хранилище.

После restart должны сохраниться:

```text
страницы
interval
ignore list
версии
история
```

Сервис должен продолжить наблюдение.

---

## 18. Redirects

HTTP redirects необходимо обрабатывать корректно.

Минимально поддержать обычные:

```text
301
302
307
308
```

Если:

```text
http://example.com
↓
https://example.com
```

тот же hostname не должен автоматически считаться другим сайтом только из-за смены `http → https`.

Необходимо сохранять:

```text
original URL
final URL
```

при необходимости также redirect chain.

---

## 19. Интервал и длительная проверка

Если:

```text
interval = 10s
request duration = 30s
```

новая параллельная проверка этой страницы не создается.

После завершения:

```text
running → idle
```

и следующая проверка запускается при очередном срабатывании scheduler.

---

## 20. Удаление страницы

Пользователь должен иметь возможность прекратить наблюдение:

```text
DELETE /pages/{id}
```

Необходимо определить судьбу истории.

Рекомендуемый вариант:

```text
soft delete
```

или полное удаление страницы вместе с версиями.

Выбранное поведение описать.

---

## 21. HTTP API

Frontend не обязателен.

Для демонстрации достаточно Swagger/OpenAPI.

Минимально:

```text
POST   /pages
GET    /pages
GET    /pages/{id}
PATCH  /pages/{id}
DELETE /pages/{id}

GET    /pages/{id}/history
GET    /pages/{id}/versions
GET    /pages/{id}/changes
```

Дополнительно можно:

```text
POST /pages/{id}/check
```

для ручной проверки.

---

## 22. Ручная проверка

При ручном запуске необходимо определить поведение, если страница уже:

```text
queued
```

или:

```text
running
```

Например:

```text
409 Conflict
```

или:

```text
уже выполняющаяся проверка считается достаточной
```

Нельзя бесконтрольно создавать второй запрос к той же странице.

---

## 23. Статистика

Добавьте:

```text
GET /stats
```

Например:

```json
{
  "pages": 42,
  "queued": 7,
  "running": 5,
  "checksTotal": 1842,
  "changed": 73,
  "errors": 14
}
```

Дополнительно:

```text
timeouts
HTTP 4xx
HTTP 5xx
average duration
```

---

## 24. Graceful shutdown

Приложение должно корректно обрабатывать:

```text
SIGINT
SIGTERM
```

При завершении необходимо:

1. остановить scheduler;
2. перестать создавать jobs;
3. прекратить принимать новые HTTP-запросы;
4. отменить или завершить текущие проверки;
5. остановить workers;
6. сохранить консистентное состояние;
7. закрыть БД;
8. завершить приложение.

---

## 25. Что не требуется

Не требуется:

- выполнять JavaScript;
- поддерживать SPA, где содержимое появляется только после JS;
- запускать браузер;
- Selenium;
- Playwright;
- визуальный screenshot diff;
- анализ изображений;
- PDF;
- видео;
- обход внутренних ссылок;
- crawler всего сайта;
- авторизация на сайтах;
- CAPTCHA;
- Kafka/RabbitMQ;
- Kubernetes.

Каждый добавленный URL является отдельной наблюдаемой страницей.

---

## 26. Обязательные технические требования

Программа должна:

- быть написана на Go;
- предоставлять HTTP API;
- иметь Swagger/OpenAPI;
- позволять пользователю добавлять страницы;
- поддерживать несколько страниц;
- иметь индивидуальный интервал проверки;
- использовать scheduler;
- использовать bounded queue;
- использовать ограниченный worker pool;
- иметь состояния `idle / queued / running`;
- исключать дублирующиеся проверки одной страницы;
- использовать HTTP timeout;
- использовать `context.Context`;
- корректно обрабатывать HTTP и network errors;
- работать только с HTML;
- проверять `Content-Type`;
- ограничивать размер читаемого HTML;
- разбирать HTML;
- поддерживать ignore list CSS-селекторов;
- нормализовать текст;
- сохранять версии;
- строить diff;
- сохранять историю проверок;
- переживать restart;
- корректно обрабатывать redirects;
- иметь graceful shutdown;
- не содержать data race.

Проект должен проходить:

```bash
go test ./...
```

и:

```bash
go test -race ./...
```

# 27. Обязательные тесты

### Первая проверка

```text
page
↓
initial version
```

### Нет изменений

Две одинаковые версии:

```text
unchanged
```

### Реальное изменение

Было:

```text
Version 1
```

Стало:

```text
Version 2
```

В history:

```text
changed
```

и доступен diff.

### Ignore list

Было:

```html
<div class="clock">12:00</div>
<p>Hello</p>
```

Стало:

```html
<div class="clock">12:01</div>
<p>Hello</p>
```

При:

```text
ignore = .clock
```

результат:

```text
unchanged
```

### Изменение полезного содержимого

```html
<p>Hello</p>
```

→

```html
<p>Goodbye</p>
```

Результат:

```text
changed
```

### Slow HTTP

```text
interval = 1s
request = 5s
```

Не должно существовать пяти параллельных проверок одной страницы.

### Ограничение workers

```text
100 pages
workers = 5
```

Одновременно:

```text
active checks <= 5
```

### HTTP 500

Сохраняется ошибка, последующая проверка все равно выполняется.

### Timeout

Один зависший сайт не блокирует остальные.

### Non-HTML

```text
Content-Type: application/pdf
```

не обрабатывается как страница.

### HTML больше лимита

```text
HTTP 200
text/html
size > max HTML
```

Результат:

```text
html_too_large
```

а не:

```text
broken link
```

### HTTP → HTTPS

```text
http://example.com
↓
301
https://example.com
```

переход корректно обрабатывается.

### Restart

После:

```text
stop
↓
start
```

страницы, настройки и история остаются.

# Главный сценарий №1 — динамический шум

Страница:

```html
<h1>Новости</h1>

<div class="clock">12:00:01</div>

<p>Go 1.30 released</p>
```

Через секунду:

```html
<h1>Новости</h1>

<div class="clock">12:00:02</div>

<p>Go 1.30 released</p>
```

Без ignore list:

```text
changed
```

Пользователь добавляет:

```text
.clock
```

Теперь:

```text
unchanged
```

После изменения:

```html
<p>Go 1.31 released</p>
```

результат снова:

```text
changed
```

То есть ignore list должен удалять шум, но не скрывать реальные изменения.

---

# Главный сценарий №2 — медленная страница

```text
interval = 2s
HTTP duration = 10s
```

Состояние:

```text
00s idle → queued
01s queued → running

02s scheduler → skip
04s scheduler → skip
06s scheduler → skip
08s scheduler → skip
10s scheduler → skip

11s running → idle
```

Очередь не должна накопить:

```text
5 одинаковых jobs
```

# Главный сценарий №3 — нагрузка

Есть:

```text
1000 pages
workers = 20
queue size = 100
```

Некоторые сайты отвечают:

```text
50 ms
```

другие:

```text
5 s
```

Сервис должен сохранять инварианты:

```text
active HTTP <= 20
queue bounded
одна page <= одна queued/running check
```

И продолжать обслуживать остальные страницы.

Главная идея задания:

```text
scheduler
↓
bounded queue
↓
worker pool
↓
HTTP
↓
DOM
↓
ignore list
↓
normalize
↓
version
↓
diff
```

Само сравнение двух строк здесь простое.

Интерес начинается, когда:

```text
HTTP медленный
scheduler срабатывает повторно
страниц тысячи
часть сайтов падает
HTML огромный
на странице постоянно меняется таймер
ignore list изменяется
сервис перезапускается во время работы
```

Именно эти сценарии делают задачу полноценным backend-сервисом, а не `time.Ticker + http.Get()`.
